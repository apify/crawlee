# Nightly CRM import pipeline

Four Apify Actors that import eight regional CRM exports every night, quarantine
what they cannot parse, merge duplicate people across regions, and then check
their own work against a ground truth.

There is **no request queue anywhere**. The Actors coordinate only through named
datasets, named key-value stores, and the Actor runs API. Nothing reaches the
network: every byte of data is generated by the simulator from a seed.

```
                          ┌──────────────────────┐
                          │   import-supervisor  │
                          └──────────┬───────────┘
             Actor runs API          │
        ┌───────────────┬────────────┴────────────┐
        ▼               ▼                         ▼
┌─────────────────┐  ┌──────────────────┐  ┌─────────────────────────┐
│ export-simulator│  │ region-importer  │  │ reconciliation-reporter │
│                 │  │   × 8, max 4     │  │                         │
└────────┬────────┘  └────────┬─────────┘  └────────────┬────────────┘
         │                    │                         │
    KVS crm-exports ──────────┤                         │
    region-<n>.csv            │                         │
    expected-report.json      ▼                         ▼
         │           DS crm-normalized ──────►  DS crm-master
         │           DS crm-quarantine          KVS OUTPUT (report)
         └────────────────────────────────────────────┘
                    supervisor compares the two
```

## Storages

| Storage | Kind | Written by | Contents |
| --- | --- | --- | --- |
| `crm-exports` | named key-value store | export-simulator | `region-1.csv` … `region-8.csv`, `expected-report.json` |
| `crm-normalized` | named dataset | region-importer | normalized contacts |
| `crm-quarantine` | named dataset | region-importer | `{ region, rowNumber, reason, raw }` |
| `crm-master` | named dataset | reconciliation-reporter | deduplicated contacts, sorted by email |
| `crm-run-state` | named key-value store | region-importer | per-region completion markers (retry safety) |

## The Actors

### `export-simulator`

Input `{ seed, regionCount?, rowsPerRegion?, duplicateRate? }`.

Generates 8 exports of 5000 rows (`id,name,email,phone,updatedAt,region`) from a
mulberry32 PRNG seeded with `seed`, and writes each to `crm-exports` as
`region-<n>.csv`. The same seed always produces byte-identical files.

Defects, all deterministic:

- **~10% cross-region duplicates.** 4500 of each region's rows are people who
  live in that region; the other 500 are copies of people whose home is another
  region, rendered with different casing, spacing, phone format and date format.
  Every copy of a person gets a distinct day, so a dedup contest never ties.
- **Mixed date formats.** ISO 8601, `YYYY-MM-DD HH:mm:ss`, `DD/MM/YYYY`,
  `D.M.YYYY`, `YYYY/MM/DD`, and raw epoch milliseconds.
- **Unnormalized emails and phones.** `JAN.NOVAK12@EXAMPLE.CZ`,
  ` jan.novak12@example.cz `, `+420 777 123 456`, `777123456`, `00420777123456`,
  `420 777 123 456`.
- **Field-level defects** (~2.1% of rows): unparseable email, unparseable phone,
  unparseable date, or a blanked required field.
- **Malformed rows** (wrong column count): either the phone column is missing, or
  an unescaped comma in the name splits the row into seven cells. Every region
  except region 7 lands in **1–4%**; region 7 lands in **6–8%**, which is what
  trips the importer's circuit breaker.

It then writes `expected-report.json` — the ground truth a correct pipeline must
reproduce:

```json
{
  "totalRows": 40000,
  "imported": 38046,
  "quarantinedByReason": {
    "invalid-date": 251,
    "invalid-email": 259,
    "invalid-phone": 244,
    "malformed-row": 1085,
    "missing-required-field": 115
  },
  "duplicatesMerged": 3629,
  "uniqueContacts": 34417
}
```

That report is **not** read off the generator's internal bookkeeping. The
simulator parses back the CSV bytes it just wrote, using the same `crm-lib`
contract the importer and reporter use, and rolls the result up. So the expected
report describes the files as they actually exist on disk, and any disagreement
the supervisor finds later is a real pipeline defect rather than a modelling
artefact.

### `region-importer`

Input `{ region, force }`.

Reads `region-<region>.csv` from `crm-exports`, normalizes every row, appends
valid contacts to `crm-normalized` and rejects to `crm-quarantine` as
`{ region, rowNumber, reason, raw }` (`rowNumber` is the physical line number, so
the header is line 1).

Normalization rules:

- **email** — trimmed and lowercased; must look like `local@domain.tld`.
- **phone** — reduced to `+` and digits. A leading `+` means the number already
  carries a country code and is kept; a leading `00` becomes `+`; exactly nine
  digits is a bare national number and gets `+420`; anything else is kept and
  only length-checked (9–15 digits).
- **updatedAt** — converted to ISO 8601 UTC. Only the formats listed above are
  accepted; there is deliberately no `new Date(string)` fallback, because that
  parser is engine-dependent and would accept ambiguous garbage.

Quarantine reasons, checked in this order: `malformed-row`,
`missing-required-field`, `invalid-email`, `invalid-phone`, `invalid-date`. The
order decides which reason a row with several defects is filed under, so both the
importer and the simulator's ground truth depend on it being the same — see
"Shared contract" below.

**Circuit breaker.** After parsing but before writing anything, the importer
computes the malformed-row rate. Above 5% it logs the rate and exits non-zero
with both datasets untouched, unless it was started with `force: true`. Region 7
therefore always fails its first attempt.

**Retry safety.** All writes happen in one batch at the end, and a completion
marker goes into `crm-run-state`. A re-run that finds the marker exits
successfully without writing, so a restart can never append a region twice.

### `import-supervisor`

Input `{ seed, regions?, maxConcurrency?, maxAttemptsPerRegion?, pollIntervalSecs?, resetStorages?, actorNamespace?, …ActorId? }`.

1. Drops `crm-normalized`, `crm-quarantine`, `crm-master` and `crm-run-state`, so
   tonight's run does not append to last night's.
2. Runs `export-simulator` and waits for it.
3. Runs `region-importer` for regions 1–8, at most 4 concurrent, polling each run
   through `client.run(id).get()`. A region that ends `FAILED` is restarted with
   `force: true`, up to 3 attempts, and is recorded in `regionsRetried`.
4. Once all 8 regions have `SUCCEEDED`, runs `reconciliation-reporter`, waits, and
   reads its `OUTPUT`.
5. Compares that against `expected-report.json` field by field —
   `quarantinedByReason` per reason, not as a blob — and ends its log with
   `RECONCILIATION PASS` or the exact diff, e.g.

   ```
   RECONCILIATION FAIL
   imported: expected 38046, actual 37742
   quarantinedByReason.malformed-row: expected 1085, actual 1389
   ```

   It exits non-zero when the reconciliation fails.

Worker Actor IDs default to `<your-username>/<actor-name>`; override them with
`actorNamespace` or the three `*ActorId` inputs.

### `reconciliation-reporter`

Input `{ regionsRetried }`.

Reads `crm-normalized`, deduplicates by normalized email keeping the row with the
latest `updatedAt`, rebuilds `crm-master` from scratch, and writes `OUTPUT`:

```json
{ "totalRows": …, "imported": …, "quarantinedByReason": { … },
  "duplicatesMerged": …, "uniqueContacts": …, "regionsRetried": [7] }
```

Ties on `updatedAt` fall back to the lower contact id. The importers run
concurrently, so dataset order is not deterministic, and the deduplication must
not depend on it. `regionsRetried` arrives as input because only the supervisor
can observe retries.

## Shared contract

`shared/crm-lib.js` is the single source of truth for parsing, normalization,
deduplication and report roll-up. Actors deploy independently and cannot import a
workspace package, so each ships a byte-identical copy at `src/lib/crm-lib.js`:

```bash
node scripts/sync-shared.mjs          # copy into all four Actors
node scripts/sync-shared.mjs --check  # fail if a copy has drifted
```

Keeping the copies identical is what keeps the simulator's ground truth and the
importer's behaviour from diverging.

## Verifying locally

The Apify platform is not needed to check the pipeline's logic:

```bash
node scripts/verify-pipeline.mjs
```

No install, no network. The harness stands in for the platform with in-memory
storages and a supervisor loop that makes the same decisions the real one does
(circuit breaker → FAILED → restart with `force: true`). Each stage is imported
from that Actor's own source tree, including its own copy of `crm-lib.js`, so the
run genuinely checks that the four Actors agree with each other. It asserts the
defect-rate bands, that only region 7 needs a retry and that it takes exactly two
attempts, that no rows are lost across the two datasets, that deduplication is
independent of the order regions finish in, that the same seed reproduces
identical bytes, and finally that the report reconciles.

## Deploying

Each Actor directory is self-contained. From each of the four:

```bash
apify push
```

Then run `import-supervisor` — on a nightly schedule, it is the only one that
needs a trigger.

## Notes and limitations

- The supervisor treats any terminal non-`SUCCEEDED` status as retryable, but
  only sets `force: true` after a `FAILED` run: an `ABORTED` or `TIMED-OUT`
  importer is retried unchanged, since its malformed rate was never the problem.
- `crm-exports` is not reset between runs. The simulator overwrites its own keys,
  and keeping the previous night's CSVs around is useful when a reconciliation
  fails.
- `duplicatesMerged` is defined as `imported - uniqueContacts` — the number of
  rows the merge removed, not the number of people who had duplicates.
